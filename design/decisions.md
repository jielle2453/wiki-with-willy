## D-026 ingest 與 note 維持分開，對帳共用規則
- 日期：2026-10-11
- 選了：維持六個 skill。補三條：(1) `rules/core.md` 加一條編號規則「出處優先序」：檔案高於使用者陳述高於推導；檔案與使用者衝突時兩者並存、各標出處，回答必須同時講兩邊。(2) `rules/synthesis.md` 範圍寫明：變動不論來自檔案或使用者口述，對綜合頁的反查與連帶處理都走這裡；ingest 與 note 本文只留一行指針。(3) 路由判準是語意的：這句話說的事，重讀檔案能不能驗證。能就是 ingest，不能就是 note。配機器後盾：ingest 開頭必跑 `kb changes`，查無變動即交 note；誤走 note 的檔案變動由下次開場的變動偵測補上。
- 為什麼：兩個 skill 真正共用的只有「連帶哪些頁要改」，已在 synthesis.md；「誰贏」是 answer 每題也要用的優先序，該住 core.md 不住 skill；其餘判斷（刪不刪問、分批、重複檔 vs 四種哪一種、寫哪個 JSON）本來就不同。「有沒有檔案名詞」只是表面特徵，反例很多（「那份報價的付款條件談好改 30 天了」有檔名卻是 note），所以判準寫原則加例子，靠 `kb changes` 當機器後盾，不寫死。
- 放棄了：合併成 update 一個 skill（省一行常駐，但描述最長、本文要分岔、三條決策重寫）；依寫入目錄 wiki/ 與 admin/ 切（路由要先判斷事實還是規則）；note 降成規則加腳本（糾正需要判斷連帶改哪些頁）。
- 重談條件：確認報告裡 ingest 查無變動後交 note 的次數，多到客戶抱怨慢。

## D-039 實體四大類
- 日期：2026-10-11

## D-094 清冊掃描與比對規則：以上次掃描為基準、快速模式只比大小時間、changes 只讀、scan 才寫
- 日期：2026-10-16
- 選了：**範圍**：登記且未排除的外部來源；總資料夾自身三區（型別夾底下除綜合卡以外的檔、收件匣、AI 產出），不掃檔案索引、系統、隱藏三樣。**跳過**：點開頭或隱藏／系統屬性的夾與檔、暫存名（`~$*`、`*.tmp`、`Thumbs.db`、`desktop.ini`、`.DS_Store`）、junction 與符號連結不跟（I-021）、開不了的夾記 error 繼續走。憑證樣式檔用守門同一份清單列著不算指紋（`read=credential`）；占位檔看 Windows 屬性不算指紋（I-020）；單檔超過 `fingerprint_max_bytes` 不算指紋只比大小時間。**比對**以清冊上次掃描為基準：新增（磁碟有清冊無、指紋對不到）、修改（大小或時間變且指紋變；指紋沒變是假變動只更新時間不報）、搬動（舊位置不見別處同指紋，換位置不報）、重複（同指紋加位置不新建）、不見（所有位置不在也沒搬，`status=missing` 記 `missing_since`；問客戶是 ingest 題）。**快速模式**（開場 hook）只比大小時間，只對既有條目變了的與大小等於某個不見條目的新檔算指紋，總讀取量上限 `changes_quick_hash_budget_bytes`（I-081）超過當修改，走訪超過 `changes_quick_seconds` 停下改印「來源很大還沒比完」。**誰寫**：`kb changes` 只讀不寫（印分類清單、`--json`）；`kb inventory scan` 把比對結果套進清冊；開場 hook 不寫清冊，只寫 `env.json` 的「已報過」記號。**整個來源找不到**（來源根展不開或不是資料夾）：條目不動不標 missing，新建 `.system/env.json`（schema 1）按機器名記 `missing_sources_reported`，開場只報一次「這台電腦找不到 X」（I-045），`kb changes` 每次都列。**開場行**：`變動：新增 N、修改 N、不見 N`，全 0 整行不印，搬動與重複不印。三個數字住 `defaults.json`。

## D-096 OOXML 內容指紋用標準函式庫先做，假變動不報
- 日期：2026-10-16
- 選了：docx、xlsx、pptx（含 docm、xlsm、pptm）除位元組 sha256 外多算一個內容指紋 `text_sha256`：`zipfile` 加 `xml.etree`，docx 以段落為單位接所有 `w:t`，xlsx 抓每格座標、值（認 `t="s"`、`inlineStr`、`str` 三種字串寫法，數值轉 float 後統一 `.10g`）與公式，pptx 以段落接 `a:t`。比對：位置已知、大小時間變、位元組變，但兩邊都有內容指紋且相同 → 假變動，現行那筆指紋的 `sha256` 原地換新、不追加、不報修改。搬動與重複仍只認位元組。zip 打不開、不是這幾種、加密 Office 檔退回位元組。這是 D-014 補「Office 指紋用抽出文字算」的第一版；ingest 題的 `kb convert` 出來後要不要改用它抽的文字，到時再看。
- 為什麼：客戶「打開看一下再存」是日常，Excel、Word、LibreOffice 存檔都重寫 zip 裡的 metadata 與 XML 排版（I-015）；不處理，開場天天報「修改 N」，跟 I-045 一樣訓練客戶不看。標準函式庫就做得到，不用等選配的 markitdown。LibreOffice 存檔改得更兇（inline string、run 重切），所以抽內容要以段落接、字串三種寫法都認；確認環境只有 LibreOffice，真客戶兩種都可能有。
- 放棄了：等 ingest 題的 convert（這題開場就會誤報）；只比 zip 成員的位元組（LibreOffice 重存 XML 整個重排，救不到）；內容指紋也用來認搬動（另存的副本會被當成搬動，位元組認法保守）。
- 重談條件：ingest 的 convert 抽出的文字跟這裡的內容指紋常不一致，或 .doc／.xls／PDF 的假變動多到客戶抱怨。

## D-111 設定檔格式：三節都是表格、同一支解析器、預設值由 `kb init` 寫進 JSON
- 日期：2026-10-19

## D-117 實體夾由 AI 寫綜合卡時建，寫錯由 `kb entity` 修
- 日期：2026-10-19
- 選了：`kb cards todo` 的「待建綜合卡」給好路徑（夾名由程式從 `entities.json` 的名稱算，含 D-043 區分詞與不能用的字元）與檔頭；AI 用檔案工具照寫，寫入工具順便建夾。守門不動：檔案工具寫 `<型別>/<名稱>/<名稱>.md` 照舊 Z1 備份放行，指令寫照舊擋。PostToolUse 驗綜合卡檔頭（編號在 `entities.json`、已確認、型別與夾名等於登記），不合就打回；AI 叫 `kb entity` 的子命令把錯的夾改名或拿掉，程式先備進回合所以退得回來。拿掉只限夾裡只有 AI 寫的那張卡；有其他檔（客戶原檔）不動、印一句請客戶看。
- 為什麼：AI 沒有退得回來的刪除與改名（檔案工具只有讀、寫、編輯；指令寫擋是因為守門讀不準指令動哪些檔、備份不了，I-106），所以刪、改名、搬都交給知道自己動哪幾個檔的程式，跟檔案卡由 `kb cards sync` 修同一條路。
- 放棄了：客戶確認時程式先建夾（確認了沒寫成卡會留空夾，每次開場提醒，I-045 同類）；守門擋「夾不存在的 Z1 寫入」（要動守門，上一條就夠）。
- 重談條件：確認階段 AI 常寫錯路徑，錯夾在客戶樹上出現的次數多。

## D-118 綜合卡檔頭快取這版只有檔案卡清單與相關實體
- 日期：2026-10-19
- 選了：D-038 的渲染快取這版只做兩欄：掛了哪些檔案卡（編號、標題、日期）、相關實體（跟這個實體共用檔案卡的實體）。全由程式從 `entities.json` 與檔案卡掛載重生，檔案卡掛載變了就重渲染受影響的綜合卡檔頭，正文不碰；觸發點在 spec 列。日程等日程題、待處理等 lint 或 answer 題再加欄。
- 為什麼：兩欄這版都有真資料可測；之後加欄只要程式重渲染每張卡的檔頭，不用製卡者重讀，比 D-116 還便宜；「有一份讀不到」answer 可以自己查 `pending.json` 拿到。
- 放棄了：這版就把「讀不到」「原檔不見」經檔案卡掛載推到綜合卡檔頭（多一個推算、三個觸發點、一組測試）。
- 重談條件：確認階段 AI 回答實體現況時常漏講有檔讀不到。

## D-119 設定檔第四節「每類最想知道什麼」：按型別一段一列，大類預設在套用時填進表
- 日期：2026-10-19
- 選了：`系統/客戶設定檔.md` 加第四節，跟第二節同一種表（型別、段落、必出現、提示；一段一列）、同一支解析器；型別欄要在第一節型別表裡。綜合卡的段落＝D-038 固定三段（現況、紀事、推算）加第四節該型別的列。`kb profile apply` 遇到第一次加入的型別、第四節沒有它的列，就把它大類的預設段落寫進第四節，來源標「推測」，再渲染 md；四大類的初始段落 spec 列。只在型別第一次加入時填，客戶之後刪光某型別的列就當「只要固定三段」不再補。`profile.json` 升 schema 2：多 `synthesis_sections` 一個清單，載入 schema 1 時遷移，對已有的型別補大類預設。
- 為什麼：預設只住 JSON 一份、客戶看得到也改得到，跟第二、三節同理（D-111 放棄藏在別處的後備）。
- 放棄了：四大類預設住程式、第四節沒寫的型別製卡時才套用（客戶看不到實際用了哪些段，兩份會漂）。
- 重談條件：客戶覺得第四節太長不想看。

## D-120 設定檔加「關於你」：客戶自己不建綜合卡、不算相關實體
- 日期：2026-10-19
- 選了：`系統/客戶設定檔.md` 多一節「關於你」，一列一個名字：名稱、是什麼（公司／本人）、別名；同一支解析器，`profile.json` schema 2 多一個清單，節的位置 spec 定。`kb profile apply` 把這幾列登記成 `entities.json` 裡標「客戶自己」的實體；製卡者從 `cards todo --json` 的設定檔塊拿到名單與別名，讀到這些名字就掛到這個實體，不另開新的。標「客戶自己」的實體不列進待建綜合卡（D-114）、不算進相關實體（D-118），檔案卡上的掛載照留。這節空著時 build-setup 問（D-052 補）；build 題之前空著就當一般實體，接受它長出一張沒人看的卡。
- 為什麼：I-079 的「客戶自己的公司出現在每張卡」用比例猜分不出它跟最大的案子；問「要不要開夾」客戶不懂夾怎麼分會說好；「你的公司叫什麼」客戶答得出來，也是建置訪談本來就會問的，填了就是程式保證。
- 放棄了：掛到一定比例以上的實體自動不建卡（大案子會被誤擋）；比例觸發問「這是你自己嗎」（設定檔沒寫時的補救，改由 build 問）；D-115 那一問多一個「不用開」（客戶會說好）。
- 重談條件：build 題之後仍常有知識庫沒填這一節；或出現客戶自己以外、一樣到處都是的實體（如母公司、唯一的大客戶）讓相關實體變雜訊。

## D-121 綜合卡跟著檔案卡更新：程式列「待更新綜合卡」，製卡者同一次整理改
- 日期：2026-10-19
- 選了：綜合卡檔頭由程式記「整理到」一欄：寫或改這張綜合卡時依據的檔案卡編號與各自的指紋。`kb cards todo` 拿它對目前掛著的檔案卡比，有新掛上的、依據的卡重做過（指紋變了）、依據的卡被拿掉，就列進「待更新綜合卡」。製卡者在同一次整理裡讀綜合卡與那幾張檔案卡，改寫現況、紀事加一行，寫完由程式把「整理到」更新成現行。這是 D-038「依據卡重做時反查、自動標待更新」的做法；共用的寫法住 `rules/synthesis.md`。
- 為什麼：跟待製卡（D-104）、待建綜合卡（D-114）同一套，程式算清單、製卡者照做；這版沒有 answer，「問到再改」的路不存在，只標不改會讓綜合卡一直停在舊的現況。
- 放棄了：只在檔頭標待更新、等有人問再改。
- 重談條件：建置期或大批丟檔時，同一個實體在一次整理裡被改太多次、製卡時間客戶等不了（可改成同一實體一次整理只改一次）。
