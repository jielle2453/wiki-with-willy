## H1 詳細（實測）
```
T1「T1 改信義王」：Edit 信義王.md（備份）→ 內容改成「T1 改過」
T2「T2 寫草稿」：Write AI 產出/x.md（create）→ PostToolUse 登記
U1「退回上一版」：
$ python <KB> versions revert
這一回合有 1 份成品：
    AI 產出/x.md
這 1 份會刪掉，確定嗎？沒有 --delete-outputs 就留著。
已退回 <T2>（問：「T2 寫草稿」）：還原 0、移除 0、成品 1 份留著
U2「確定，刪掉」：
$ python <KB> versions revert --delete-outputs
已退回 <T1>（問：「T1 改信義王」）：還原 1、移除 0、成品 0 份
結果：信義王.md 回到 T1 之前的內容（T1 的修改不見了），x.md 還在
```
原因：T2 已經有 `reverted.json`；U1 這個退回回合沒有任何 manifest 行（Z3 的 create 沒加旗標就跳過）；所以候選清單的第一個變成 T1。如果 U1 有 manifest 行，第二次跑則會變成「退回剛才的退回」。目前沒有子命令能「只刪某個已退回回合的成品」，spec 的流程本身走不通，要由設計 session 決定做法，例如 `revert` 不帶旗標時先只列出成品、不動手，等確認後再整批執行；或者另做一個刪成品的子命令。T1 可以靠再退一次救回來，但 AI 會照實回報「已退回 T1…還原 1」，客戶不一定看得出出錯了。

## plugin-dev 審查

依據：`plugin-dev:hook-development`，加上官方 hooks 文件的欄位定義。

- **hooks.json**：plugin 格式正確（`description` 加 `hooks` 包一層）。UserPromptSubmit 沒有 matcher，正確，matcher 對這個事件沒有作用。PreToolUse 的 matcher 沒變。PostToolUse matcher 是 `Write|Edit|MultiEdit|NotebookEdit`。三支都是 `type: command`，指令是 `python "${CLAUDE_PLUGIN_ROOT}/hooks/…"`，有加引號，timeout 分別是 5、10、10。
- **turn.py（UserPromptSubmit）**：
  - 什麼都不印。這點必要，因為這個事件 exit 0 時印出的東西會被加進 context。
  - 永遠 exit 0，例外寫進 hook-errors.log。
  - 輸入讀 `prompt`，沒有才讀 `user_prompt`。skill 文件寫的欄位名是 `user_prompt`，官方文件和實際 payload 是 `prompt`，兩個都讀是對的（疑義裁定 3）。`source` 欄在 UserPromptSubmit 沒有文件記載（SessionStart 才有），這段判斷實際上不會觸發，無害。
- **output_log.py（PostToolUse）**：
  - 什麼都不印，exit 0。
  - 用到 `tool_name`、`tool_input.file_path`／`notebook_path`、`cwd`、`session_id`，沒用到 `tool_response`／`tool_result`（skill 和官方文件這裡的名稱不一致，剛好避開）。
  - 工具執行失敗時 Claude Code 不觸發 PostToolUse，所以不會登記沒寫成的檔。
- **guard.py（PreToolUse）**：
  - 輸出 `hookSpecificOutput{hookEventName, permissionDecision, permissionDecisionReason}`，這是現行格式。skill 範例少了 `hookEventName`，那份範例比較舊。
  - 備份失敗或大改動時改印 deny，ledger 多一行。
  - Python 內部的任何例外都會 fail closed。
  - 缺口是 Python 以外的失敗：逾時（M1）、找不到 `python`（I-103、B-016、B-020）都會 fail open。
- **跨 hook 的假設**：PreToolUse 備份、PostToolUse 登記，兩個不同事件之間保證先後順序，沒有依賴同一事件內多個 hook 的平行順序。L2 是「PreToolUse 放行以後寫入不一定真的發生」，這是 hook 模型本身的限制。
- **plugin-validator agent**（整個 worktree，唯讀，`git status` 前後都乾淨）：判定 PASS，0 個 critical、4 個 warning、6 個 minor。`claude plugin validate` 的輸出：
  ```
  ⚠ Found 1 warning:
    ❯ root: CLAUDE.md at the plugin root is not loaded as project context. …
  ℹ Advice: README.md has no line that installs "wiki-with-willy" from a marketplace. …
  ✔ Validation passed with warnings
  ```
  - warning：
    - 裸 `python`，缺了或逾時都會 fail open（已知 I-103、B-020）。
    - PreToolUse 裡的 `shutil.copy2` 遇到大檔或雲端同步的慢碟可能超過 10 秒（和 M1 同一類）。
    - 備份先於寫入（L2）。
    - 根目錄的 CLAUDE.md 不會被載入（已知）。
  - minor：
    - `plugin.json` 的 author 是 plugin 名稱，也沒有 homepage／repository。
    - README 沒有 marketplace 安裝那一行。
    - `MultiEdit` 已經不是現行工具名，留著無害。
    - `source`／`user_prompt` 的防禦性程式碼。
    - 守門 allow 會蓋過使用者設的更嚴的權限模式（D-073 的設計）。
    - `str(target)` 可能變成 `"None"`，目前碰不到。
  - jq 不在，所以沒跑 `validate-hook-schema.sh`（B-020）。

結論：hook 介面和輸出格式都沒問題。真正的風險在 M1：10 秒逾時對上 60 秒的鎖等待。

## 給設計 session 的 spec 問題
1. 驗收 5 的路徑 `案子/信義王/新卡.md` 是 Z2，會被守門 deny；第 13 條暗示要用 `案子/新卡/新卡.md`。建議改路徑。
2. 驗收 20「任一 hook 餵壞 JSON：stdout 空」和守門 D-034 衝突：知識庫內 `guard.py` 收到壞 JSON 會 deny。建議改成「turn.py、output_log.py 任何情況都 stdout 空；guard.py 不在知識庫時 stdout 空、在知識庫內 deny」。
3. 驗收 18 只點名守門 11 是預期改變，守門 28 的兩句也從 pass 變成 deny Z3 shell_write（同一張決策表造成的）。建議一起列進去。
4. 第 6 節 4 和 CLI 輸出範例的句子不一致，而且「確認後刪除」沒有一條走得通的子命令（H1）。

6. FileLock 的 timeout 60 秒（第 4 節）和 hook timeout 10 秒（第 1 節）都是 spec 指定的值，兩個放在一起就造成 M1。要由設計決定：縮短 hook 裡用的鎖等待（短於 hook timeout，逾時就 deny），還是拉長 hook timeout。
