## 不過的清單與判斷

1. **選項編號在畫面上變成 a～i**（第 1、2 步）。判斷：**實作錯**。SKILL 本文「回答」那段只寫「把結果照 `n` 與 `label` 列成編號選項」，沒有樣子可看，也沒禁止把題目編號；spec 的「AI 回答末尾的樣子」範例是對的（題目不編號、選項頂層編號），但這個範例沒進 SKILL。建議在 SKILL 的回答骨架放這個範例的縮影，並寫明題目不編號、選項用頂層 `1.` 清單。
2. **先答再整理沒做到**（第 3 步）。判斷：**實作錯為主，spec 有一半責任**。SKILL 有「客戶問的先答」原則與骨架開頭那句，但模型仍在最前面只說「我先查」，答案放最後。spec「不做」一節明講程式不保證先答（B-058），所以只能靠文字；現在的文字夠清楚卻沒擋住，需要更具體的做法，例如在骨架第 0 步寫成「先寫出答案那一段，再叫 `changes`」，並說明答案要含數字與出處。若設計 session 要程式保證，那是另一題。
3. **工具之間的中文自言自語**（第 3 步）。判斷：**不在這題的範圍**。規則在 hook 的核心規則 R-10，`hooks/` 與 `rules/` 在這題「不可以動」。這題的 SKILL 沒有加重也沒有消除。建議另開一題。
4. **客戶沒回答「是不是你刪的」，綜合卡就先把依賴它的句子拿掉**（2a）。判斷：**待設計判斷**，屬 `rules/synthesis.md` 的行為。「卡先留著」與「綜合卡拿掉它」互相不一致。
5. **綜合卡寫入被擋「檔案在讀過之後被改動」**（第 3 步）。判斷：次要，疑似程式在寫卡時重寫了綜合卡檔頭。AI 自己重讀再寫恢復了，多花一輪。不在這題範圍，列為觀察。

## 結論
- 第 1 步：部分過。順序、上限、連號都對；畫面上選項變字母，是實作問題。
- 第 2 步：過。回編號、「好」不刪、「刪了」才刪，三個關鍵行為都對，指令跟 spec 一字不差。
- 第 3 步：不過。報價答案對、整理有做，但先答再整理沒做到，且過程有中文自言自語。
- 整體：整理 ingest 的核心（`plan`／`asks` 照程式做、strict 刪除、編號跨題接著編且不撞）在實機上成立。要修的是 SKILL 回答段的格式與「先答」寫法，屬實作文字，不需要改 spec 的決定。
