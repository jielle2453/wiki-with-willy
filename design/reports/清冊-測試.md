## 發現（實跑證實，驗收準則沒涵蓋）

### 發現一（高）：開場快速比對時，單檔算指紋停不下來，會超過 SessionStart 的 10 秒逾時
- 位置：`hooks/session.py` 的 `_quick_scan`；`inventory.py` 的 `digest_of`／`text_of`（456-476）、`sha256_of`（141）；`content_fp.text_fingerprint`。
- 原因：`_Stopper` 只在開始算一個指紋之前查時間（裁定 31）。`sha256_of` 一次讀完整個檔，`content_fp` 用 `ET.parse` 把整份工作表解成 DOM，兩者中途都不查時間。讀取預算 200 MB 只算位元組指紋，不算解壓後的 XML。
- 實測：我用自己產生的 xlsx，一張工作表、5 欄數字。先全掃，再改一格，然後量開場：

  | xlsx 大小 | `text_fingerprint` 單獨 | 開場 hook 總時間 |
  |---|---|---|
  | 5.8 MB（30 萬列） | 6.18 s | 8.00 s |
  | 11.7 MB（60 萬列） | — | **13.99 s** |

  `hooks.json` 裡 SessionStart 的 `timeout` 是 10。
- 後果：
  - hook 被砍時，整段 `additionalContext` 都沒有：kb 行、`core.md` 都進不來，哨兵句會誤判（裁定 31 想擋的正是這件事）。
  - 快速比對不 apply，所以只要沒人跑 `kb inventory scan`，之後每次開場都會再超時。
  - 開場看不到變動行，AI 也就不會建議去 scan，這個狀態不會自己好。
  - 在 HDD、網路磁碟、雲端資料夾上，200 MB 的位元組指紋本身也可能超過。
- 建議（設計 session 定）：
  - 快速模式每讀一塊就查一次時間。
  - 快速模式不算內容指紋，或內容指紋設單檔上限。
  - 或給快速模式另設一個比較小的單檔上限。

### 發現二（高）：OOXML 壓縮資料壞掉時丟 `zlib.error`，`content_fp` 沒接住
- 位置：`scripts/kb/_lib/content_fp.py:42` 的 except 只列了 `BadZipFile, KeyError, ParseError, OSError, ValueError, EOFError`。
- 實測：組一份正常的 docx，再把 `word/document.xml` 的壓縮資料翻掉 40 個位元組，模擬同步到一半的檔。
  - 直接呼叫 `text_fingerprint`：丟 `zlib.error: Error -3 while decompressing data: invalid bit length repeat`。
  - `kb inventory scan`：traceback，exit 1。
  - `kb changes`：traceback，exit 1。
  - `kb folders add <含這份檔的夾>`：traceback，exit 1。sources.json 的 md5 從 `e8f0760f7c5f` 變成 `445ce2db8fcd`（已登記），清冊 md5 `ec7a6542ce47` 沒變（沒入冊），也沒有程式段。重跑同一個指令被拒：`和既有來源「壞檔夾」重疊…`。
  - 開場：這份是新檔、大小不相符，快速模式不算它，所以沒事。換成已登記的檔變壞、而且大小時間變了，快速模式就會算到它，例外被 `_quick_scan` 接住只記 log，變動行和找不到來源行都不見。
- 同類的還有加密的 zip 成員（`RuntimeError`）、不支援的壓縮方式（`NotImplementedError`）。這兩種沒實測，只讀碼確認 `zipfile` 會丟這些例外。
- 建議：`text_fingerprint` 什麼都抓不到就回 None，退回位元組指紋，這也符合 D-096「抽不出來就退回位元組」。`folders` 的清冊階段失敗時要怎麼收，見發現三。

### 觀察（第二輪，都是低）

- **2-1. 內容指紋的「每 1000 個元素查一次」在每個 zip 成員重新計數**（`content_fp._events`）。小成員很多的檔永遠不會問到時間。實測一份 3000 張投影片、每張約 400 個元素的 pptx：喊停的函式被呼叫 **0 次**，喊停也照樣算完，但全程只要 0.77 s。目前影響小，投影片或工作表多又大時才會拖時間。建議計數跨成員共用，或每個成員開頭先問一次。
- **2-2. hidden 排除只拿掉重複檔其中一個位置時，第二行印「0 份已拿掉」**。實測：把一份既有檔複製到 `客戶案件/私人/`，再 `exclude 私人 --kind hidden`。清冊裡 `私人` 0 筆（位置確實拿掉了），`--json` 卻是 `{"excluded": 0, "removed": 0}`，人看的那行是 `清冊：0 份已拿掉`，AI 轉述時會說「沒拿掉任何東西」。建議數拿掉的位置數，或句子改成「N 個位置」。
- **2-3. `versions revert` 遇到壞清冊時，最後那句「清冊讀不到」是還原之前的狀態**。實測還原後清冊已回到 schema 2、讀得到，但仍印 `清冊讀不到：…`。建議還原後再讀一次，讀得到就改說「已從備份還原」。
- **2-4. 快速模式內容指紋算到一半喊停時回 None，跟「不是 OOXML」分不出來**。假變動的大 OOXML 在開場會被算成修改。開場因為 `incomplete` 印的是「還沒比完」，`kb changes --quick` 則會列出這個修改，但有「還沒比完」的提示。只讀碼，沒實測。
- **2-5. iterparse 改寫後，記憶體仍隨格數長**。cleared 的元素還掛在樹上，code-review 的疑點。實測同一份 11.7 MB xlsx（300 萬格）在 tracemalloc 下峰值 330 MiB，其中包含輸出那 300 萬行字串本身，程式碼沒變的部分省不了。不影響正確性。
- **2-6. 清冊讀不到時跑 `versions revert --delete-outputs`，回報「成品 0 份」**，但那回合 manifest 記成 create 的 Z3 檔照樣刪掉，刪掉的會列在「移除 N」裡。清冊正常時也是同一個迴圈，而且只有使用者明說時才刪，所以不算退步。只讀碼。
- **2-7. 其餘 code-review 候選**：
  - `kb changes` 只剩 restored／duplicates 時不印套用那句：這兩類本來就不在 changes 的列表裡，第一輪也一樣；裁定 42 已收下目前做法。
  - 清冊寫成功後才在 `_inventory_bytes` 讀檔失敗，會把 sources.json 退回：理論上可能，沒實測。
  - docx 有巢狀段落（文字方塊）時，輸出順序跟第一輪的實作不同：還沒發行，沒有存下來的指紋，不影響使用者。
  - `versions list` 每個回合各讀一次清冊：只是效能。
