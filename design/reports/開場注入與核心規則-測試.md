### 其他發現（低，不擋）
- L1 `hooks/session.py:86`：寫完 stdout 沒有在 try 裡 `flush()`（`hooks/guard.py:32` 有）。萬一 pipe 已經關了，flush 會延到直譯器結束才做，那時已經在例外處理外面：stderr 印 `BrokenPipeError`，exit 120 不是 0。不擋，但跟「永遠 exit 0、不印」的約定不一致（security-review）。
- L2 `turn.py:46` 的正規式 `[^>]*`：屬性值裡如果有 `>`（`title="a>b"`），標籤會剩一截留在「問」裡。另外，很長的 prompt 裡塞很多沒閉合的 `<pasted_content`，掃描是平方時間，最壞會讓 UserPromptSubmit 逾時，結果只是這一句沒記。只有客戶自己打得出來（code-review、security-review）。
- L3 `hook-errors.log` 的訊息是 `str(e)[:200]`。如果是 `read_core()`／`plugin_root()` 的 FileNotFoundError，訊息會帶 plugin 的絕對路徑，寫進知識庫的 `.system/hook-errors.log`。log 算不算 D-019 說的「狀態檔」由設計 session 判斷；這不是外洩（security-review）。
- L4 `tests/test_hooks_session.py:82`：2 秒上限是冷啟動計時。實測 0.06 秒，但機器忙或防毒掃描時有機會偶發紅燈（code-review）。spec 驗收 7 本來就要求 2 秒，這裡只是提醒。
- L5 `tests/test_budget.py:137-143`：`opening_status` 沒看子程序的 exit code 和 stderr；用的是裸 `assert`，`python -O` 會被拿掉。常駐合計沒算隔開用的 `\n\n` 那 2 字（code-review）。

- **`os.dup2`**：實測用 Popen 先把 stdout 讀端關掉，再送 startup payload：`closed stdout: exit 0 stderr b''`。測試框架自己的 reader thread 印了 `ValueError: read of closed file`，那是我這邊的，跟 hook 無關。
- **空格換法**：`" ".join(text.split())` 會把多的空白壓掉，spec 例句結果不變（驗收 15）。
