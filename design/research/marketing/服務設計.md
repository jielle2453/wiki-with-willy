# 服務設計：LLM-wiki 代建服務

資料日期：2026-10-04。這份文件把目前為止的決策、問題定義、服務流程、範圍、場景與賣點整理在一起。依據是 [使用者痛點](../reports/使用者痛點.md)、[競品分析](../reports/競品分析.md)、[Persona](../reports/Persona.md)、[Journey Map](../../reports/Journey Map.md)，實作基底是 [Karpathy 的 LLM Wiki 原文](../reference/karpathy-llm-wiki.md)，plugin 的技術設計在 [spec](../design/spec.md)。

**提醒：** 除了一筆訪談與產品負責人自己的實測，其餘都是二手資料與推論。賣點、價格與流程都還沒有經過真實客戶驗證。

## 結論先講

1. **賣的是代建服務，不是軟體。** 接案形式：了解需求、建置、兩週磨合。plugin 是你的工具箱，也是交付物。
2. **客戶是願意付費的人：** 小老闆，以及有預算的專業工作者。受薪職員不是客戶。
3. **第一版範圍：** 單人使用，來源是資料夾。Email 延後再議。
4. **核心價值：** 不用整理，就能問自己的資料，每個答案都指出出處。
5. **你的優勢是磨合經驗。** 它會變成兩樣東西：需求訪談的問題清單，以及 plugin 內建的預設規則。
6. **三個最大的風險：** 沒有付費意願的證據、「不看客戶資料」不容易完全做到、兩週後壞掉時誰負責。

## 一、已定的決策

| 項目 | 決定 |
|---|---|
| 商業模式 | 只賣代建，接案形式 |
| 服務內容 | 前期了解需求 → 建置 → 約兩週磨合 |
| 產品形式 | 通用的 plugin 基底，每個客戶再調整 |
| 實作基底 | Karpathy 的 LLM Wiki 原文 |
| 長期範圍 | 多來源（資料夾、雲端硬碟、Email、Line）、主動推送、團隊共享 |
| 第一版範圍 | 單人；資料夾。Email 不在第一版，延後再議 |
| 客戶使用的介面 | Claude 桌面程式的 Cowork（已測試可用） |
| plugin 的設計方式 | 從頭設計通用架構，再用你的經驗修正；不直接沿用你自己的系統 |
| 建置方式 | 你用 Claude Code 做前期工作：載入 plugin、指向資料夾、執行建置；不看客戶的內部資料 |
| 磨合期後 | 新需求另外收費；其餘問題靠 AI 自己解決 |
| 驗證方式 | 不再做訪談，改用實際案子與原型試用 |

## 二、要解決的問題

| # | 問題 | 誰最明顯 | 證據 |
|---|---|---|---|
| 1 | 看不出用途：不知道 AI 能用在自己哪件工作上，也不知道該問什麼 | 一般員工 | 強（44% 認為幫不上工作，只有 10% 是不會用） |
| 2 | 前期門檻與挫敗：安裝、設定、要一步步教 AI | 所有非技術使用者 | 強（你的經驗、訪談、會計業 41% 卡在導入時間） |
| 3 | 整理是使用者的工作：要搬檔、要維護，最後放棄 | 試過整理工具的人 | 中 |
| 4 | 不可信：答案無法查證、失敗不提示、不知道 AI 改了什麼 | 專業工作者 | 強 |
| 5 | 資料去向不明：怕外流，規範也可能不允許 | 公部門、經手客戶資料的人 | 強 |
| 6 | 付費的人和使用的人常常不同 | — | 中 |

## 四、這個點子是否符合使用者需求

**結論：方向符合，但符合的對象比最初設想的窄。**

| 最初的假設 | 證據 | 判斷 |
|---|---|---|
| 很多人想用 AI 但沒時間學 | 對老闆成立；對一般員工，主因是看不出用途 | 部分成立 |
| 初期成本與門檻太高 | 你的經驗、訪談、現有實作的安裝問題都支持 | 成立 |
| 幫他們建好環境，他們只要用就好 | 建置門檻可以消除；不知道問什麼、要查核答案這兩件事不會自動消失 | 部分成立 |
| 做成通用的 plugin | 沒有人做出同樣的組合；代建模式下「通用」是指可重複使用的基底，風險降低 | 成立 |
| 讓 AI 幫忙文件管理 | 使用者要的是不用管理就找得到、用得上 | 需要改說法 |

**符合的地方：**

- 問題 2、3 是核心，也是競品共同的弱點。
- 你的實測中答案都附原檔位置，這是使用者最稱讚的能力。
- 代建加兩週磨合，正好對應買方最常抱怨的「交付後沒人管」。

**缺口：**

- 客戶仍然要自己訂閱 Claude 付費方案並安裝桌面程式。
- 無法服務要求資料完全不上傳的人。
- 文件很少的人用 NotebookLM 就夠了。
- 改動紀錄與退回功能還沒有。

**兩個最大的未知：**

1. 夠不夠痛到願意付錢。唯一的訪談對象說不夠痛。
2. 非技術使用者能否承擔查核 AI 內容的負擔。

## 五、目標客戶

| Persona | 在代建服務中的角色 | 理由 |
|---|---|---|
| 老闆：掌握預算、沒時間學 | **主要客戶** | 自己決定預算；瓶頸是時間 |
| Lin：想保有主導權的專業者 | 客戶 | 願意為好工具付費；要求可查證、可退回 |
| 小宜：第六次嘗試的整理者 | 客戶，視預算而定 | 痛點最強；個人付費上限較低 |
| 阿凱：被要求用 AI 卻沒人教 | 使用者，不是買方 | 可能是老闆付錢後的實際使用者 |
| 主任：受規範限制 | 不是客戶 | 不付費；個資不能交給雲端 AI |

**適合接的案子：** 文件數量多、分散在資料夾與信箱、時間可以換算成錢、可以接受資料送到雲端處理。

**不適合接的案子：** 要求完全離線、主要內容是個資或受規範限制的資料、只有十幾份文件、需要多人權限控管（第一版）。

## 六、服務流程

| 階段 | 你做什麼 | 客戶做什麼 | 客戶得到什麼 | plugin 提供 |
|---|---|---|---|---|
| 0 洽談 | 用公開資料的示範庫展示效果；了解對方的工作 | 看示範、提問 | 看到實際效果再決定 | 現成的示範知識庫 |
| 1 需求訪談 | 問清楚資料在哪、最常找什麼、哪些不能碰 | 回答問題；指出要排除的資料夾與信件 | 一份確認過的範圍：來源、場景、排除清單 | 訪談問題清單；資料夾結構掃描 |
| 2 建置 | 用 Claude Code 載入 plugin、指向資料夾、套用並調整規則、執行建置 | 登入自己的 Claude 帳號；授權 Email 連接 | 建好的知識庫 | 預設規則、建置指令、讀取失敗清單 |
| 3 交付 | 帶客戶問幾個真實問題；說明資料去向；教五句常用的話 | 實際操作 | 一張速查卡；知道怎麼用、怎麼查證 | 依內容產生的建議問題 |
| 4 兩週磨合 | 收集答錯或不順的地方，調整規則 | 日常使用並回報 | 越來越合用的知識庫 | 問題回報方式；改動紀錄 |
| 5 結案 | 最後一次健檢；說明之後如何自己維持 | 確認驗收 | 能自己運作的知識庫 | 自動更新與健檢 |

**你的磨合經驗放在哪裡：** 階段 1 的訪談問題（知道該問什麼），以及階段 2 的預設規則（不必從零教 AI）。

### 不看客戶資料，要怎麼做到

你的做法是操作 Claude Code 做前期工作，但不看客戶的內部資料。實務上有幾個地方會碰到內容，需要事先設計：

| 會碰到內容的地方 | 建議做法 |
|---|---|
| 建置時畫面會顯示 AI 正在讀的內容 | plugin 提供只顯示進度與檔名的模式；或由你設定好之後，讓客戶自己按下執行 |
| 檔名與資料夾名稱本身可能敏感 | 事先告知客戶你會看到結構與檔名，取得同意 |
| 確認品質需要看答案 | 由客戶自己問五個問題並回報對或錯，你不看答案內容 |
| 磨合期回報問題 | 回報格式只描述問題類型；需要看內容時逐次取得客戶同意 |
| Email 授權 | 由客戶本人登入授權，你不經手帳號密碼 |

**務實的標準：** 完全看不到很難做到。比較可行的承諾是「我只會看到資料夾結構與檔名，不會開啟任何檔案內容」，並寫進保密協議。

### 磨合期後的支援

| 情況 | 處理 |
|---|---|
| 新需求（新的來源、新的場景、新的使用者） | 另外報價。客戶自己用 AI 做（例如自己加資料夾、甚至自己建置）不擋，磨合問題自己克服；找我們代做才收費（2026-10-10） |
| 答案不夠好、規則要微調 | 知識庫應能透過對話自行修正並記住 |
| 新增的檔案與信件 | 自動納入 |
| 平台或模型改版導致功能失效 | **未定**。這不算新需求，AI 也無法自己解決，需要約定處理方式 |

最後一項建議在合約裡寫明，例如結案後一定期間內免費修復，之後按次計費。

## 七、範圍

### 第一版

| 項目 | 範圍 |
|---|---|
| 使用者 | 單人 |
| 來源 | 本機與雲端硬碟同步的資料夾 |
| 檔案格式 | Word、Excel、PowerPoint、PDF（含掃描檔）、純文字與 Markdown |
| 語言與平台 | 繁體中文；Windows 為主 |
| 建置環境 | 你用 Claude Code 建置；客戶日常用 Claude 桌面程式的 Cowork |

### 之後的階段

| 階段 | 內容 |
|---|---|
| 二 | Email；行事曆；主動推送（會前背景、逾期承諾）；Line |
| 三 | 團隊共享；個人與團隊空間分開 |

### 不做

- 自建桌面應用。
- 本機模型版本。
- 知識圖譜視覺化。

### 每個案子要約定的事

接案最常見的問題是範圍膨脹。建議每份報價都寫明：

- 幾個資料來源（哪些資料夾、哪個信箱、信件的時間範圍）。
- 幾個使用場景。
- 排除清單。
- 磨合期的長度與包含的調整次數。
- 驗收標準：不出題，磨合期內依功能清單確認（2026-10-10 決定）。

訪談問題、告知事項、合約草稿與驗收方式見 [接案文件](接案文件.md)。

## 八、共同場景

| # | 場景 | 客戶會說 | 系統做什麼 | 成功標準 | 優先 |
|---|---|---|---|---|---|
| 0 | 建置（一次性） | 由你執行 | 掃描來源、套用規則、分批建立、列出讀不到的項目 | 客戶不寫設定、不搬檔 | 必要 |
| 1 | 問我的資料 | 「去年跟某客戶談的條件是什麼？」 | 跨檔案與信件回答，附原檔或原信的位置；找不到就說找不到 | 答案可點回出處 | 必要 |
| 2 | 找檔案、找信 | 「那份報價單在哪？」「誰寄過那個附件？」 | 指出位置，必要時列出候選 | 比自己翻快 | 必要 |
| 3 | 掌握背景 | 「這個專案目前的狀況？」 | 整合文件與往來信件成摘要，每一點附來源 | 五分鐘內看完 | 必要 |
| 4 | 參考舊資料起草 | 「照上次的格式寫一份新的」 | 找出舊文件、產出新檔並存成檔案 | 得到檔案而不是一段對話 | 第二 |
| 5 | 追蹤承諾 | 「我答應過誰什麼還沒做？」 | 從信件與會議記錄整理待辦與承諾 | 不漏掉 | 第二 |
| 6 | 答案存回 | 不需要說 | 有價值的比較與分析存成 wiki 頁面 | 知識庫越用越豐富 | 第二 |
| 7 | 保持最新與健檢（背景） | 不需要說 | 檢查新增與變動；回報過期內容；改動可退回 | 客戶不必維護 | 必要 |

- 場景 0、1、2、3、7 是每個案子都交付的基本內容。
- 場景 4、5、6 依需求訪談的結果決定是否納入。
- Email 不在第一版：場景 2 的「找信」與場景 5 延後；場景 1、3 第一版只涵蓋檔案。
- 場景 6 來自 Karpathy 原文，是和 NotebookLM 最大的差別。

以 Karpathy 原文為基底的架構對應，以及 plugin 的組成，見 [spec](../design/spec.md) 第二、五節。

## 九、市場缺口與賣點

### 缺口

| 使用者要的 | 現有選擇給的 | 缺口 |
|---|---|---|
| 不用整理就能問到答案 | Notion、Obsidian 要自己維護；NotebookLM 要挑檔上傳 | 整理仍是使用者的工作 |
| 知識會累積 | NotebookLM 與一般檔案上傳每次都從頭找一遍 | 沒有累積 |
| 答案能對回原始檔案 | 多數 LLM-wiki 只連到 AI 寫的摘要頁 | 無法查證到源頭 |
| 不懂技術也能用 | 現有 LLM-wiki 幾乎都要終端機與 API 金鑰 | 目前是工程師的玩法 |
| 繁體中文、Windows 正常運作 | 現有實作有中文路徑與編碼錯誤 | 台灣使用者沒有被照顧 |
| 有人幫忙弄好並陪著用 | 台灣只有課程與教學文章 | 沒有找到代建服務 |

### 定位

> 給資料散在各處、沒時間整理的人：我幫你建一個會自己整理的 AI 知識庫。不用整理、不用搬檔，就能問到答案，每個答案都指出是哪一份檔案、哪一封信。建好之後陪你用兩週，調到合用為止。

### 賣點

| # | 賣點 | 一句話 | 證明方式 |
|---|---|---|---|
| 1 | 不用整理 | 資料夾和信箱維持原樣，AI 自己讀、自己整理 | 示範：指一個亂的資料夾，建好後問答 |
| 2 | 每個答案都有出處 | 點一下就打開原始檔案 | 示範中實際點開 |
| 3 | 越用越懂你 | 問過的、整理過的都會留下來 | 一週後的前後對照 |
| 4 | 我幫你建好，陪你用兩週 | 不用學、不用設定；不合用就調 | 明確的服務流程與驗收標準 |
| 5 | 你的資料不會被動到，我也不會看 | 原檔只讀不改；我只看得到資料夾結構 | 保密協議與白話的資料說明 |

### 不要說的話

- 「資料不會離開你的電腦」：內容會送到雲端處理。
- 「每天省下 2.5 小時找資料」：這個數字是估計值，不是實測。
- 「LLM-wiki」「第二大腦」：一般人聽不懂。
- 「取代 Notion」：團隊功能完成前不成立。

## 十、如何取得客戶

研究顯示這類服務最大的困難是讓人在付錢前相信有用。

1. **示範是核心。** 準備一個用公開資料建好的示範知識庫，洽談時現場操作。
2. **從身邊的人開始。** 前兩三個案子用優惠價，換取案例故事與推薦。
3. **案例按職業寫。** 通用服務要靠具體案例讓人看出用途，例如「接案設計師怎麼用」「補習班老闆怎麼用」。
4. **繁中內容。** 台灣已有不少介紹 LLM-wiki 的文章，讀者知道概念卻用不了。「不用自己動手的版本」是切入點。
5. **固定價格、明確交期、可運作的成品。** 買方最反感的是範圍模糊的月費與只交簡報的顧問。

### 價格參考

| 類型 | 價格 | 備註 |
|---|---|---|
| 英語市場的個人代建 | US$600–3,500 | 只是開價，沒有成交數據 |
| 台灣 AI 顧問專案 | NT$10 萬起 | 以企業為對象 |
| 台灣線上課程 | 約 NT$3,000 | 個人願意付的價位 |

台灣的個人代建沒有成交數據，要靠前幾個案子測試。

### 要先讓客戶知道的事

完整清單（洽談 9 項、交付 7 項）見 [接案文件](接案文件.md) 第三節。

- 需要自己訂閱 Claude 的付費方案。
- 資料會送到雲端處理，可以排除指定的資料夾與信件。
- 你會看到資料夾結構與檔名，不會開啟內容。

## 十一、待決策：建置時用訂閱還是 API 製卡

狀態：未決定，產品負責人之後決策。以下數字都是粗估，實際可能在一半到兩倍之間，需以 [spec](../design/spec.md) 待驗證第 8、10 項校正。

### 兩種做法

| | 訂閱製卡（目前 spec 的做法） | API 製卡 |
|---|---|---|
| 做法 | 在 Claude Code 中由 AI 逐份讀檔寫卡 | 一支程式每份檔案呼叫 API 一次：送出核心規則與客戶設定（快取）加上檔案文字，取回一張卡 |
| 每份檔案的消耗 | 約 1 萬到 2 萬 token（每一步都重送規則與對話） | 約 1 萬 token，其中約 4,000 是快取的規則 |
| 計費 | 訂閱方案的使用額度 | 按 token 計費 |
| 限制 | 每五小時與每週的額度上限，中型以上可能要分多天並請客戶升級方案 | API 帳號的速率限制；用 Batch API 則整批送出、非同步完成 |

### 訂閱製卡的級距

| | 小 | 中 | 大（第一版上限） |
|---|---|---|---|
| 檔案數 | 約 300 | 約 1,000 | 約 2,000 |
| 建置總 token | 300 萬–600 萬 | 1,000 萬–2,000 萬 | 2,000 萬–4,000 萬 |
| 逐份處理的時間 | 3–5 小時 | 8–17 小時 | 17–35 小時 |

訂閱方案的確切額度沒有公開，需要多少天只能實測。

### API 製卡的成本

**價格**（Anthropic 官方 API，每百萬 token，美元；取自 2026-09-25 的資料）：

| 模型 | 輸入 | 輸出 | 快取讀取 |
|---|---|---|---|
| Claude Opus 5.5 | 4 | 20 | 0.20 |
| Claude Sonnet 5.5 | 2 | 10 | 0.20 |
| Claude Haiku 4.5 | 1 | 5 | 約 0.10 |

Batch API 打五折，非同步處理，通常數小時內完成，最長 24 小時。

**每 1,000 份檔案**（假設每份 5,000 token 文字、4,000 token 快取規則、輸出 1,000 token）：

| 模型 | 一般 API | Batch API | 約新台幣（Batch） |
|---|---|---|---|
| Opus 5.5 | 約 US$40 | 約 US$20 | 約 NT$650 |
| Sonnet 5.5 | 約 US$20 | 約 US$10 | 約 NT$330 |
| Haiku 4.5 | 約 US$10 | 約 US$5 | 約 NT$170 |

變動來源：Opus 5.5 與 Sonnet 5.5 的思考 token 按輸出計價（製卡設為低強度）；掃描檔每頁約 1,500–2,000 token；Excel 與長文件的文字量差異大（程式限制每份讀取長度）。

### API 製卡的好處與代價

| 好處 | 代價 |
|---|---|
| 成本低，盤點後可算出接近的金額 | 製卡改為呼叫 API 的程式，[spec](../design/spec.md) 第四、五節要修改 |
| 不受訂閱額度限制，建置不必分多天 | 要多寫一支製卡程式 |
| 製卡可用較便宜的模型，查詢仍在 Cowork 用強的模型 | 之後在 Cowork 更新時用的是訂閱，兩邊的製卡品質要保持一致 |
| 每份檔案走同一流程，結果一致 | 需要決定 API 帳號歸屬 |
| API 屬商用條款，預設不用於訓練，保存 30 天 | — |

### 若採用 API，帳號歸屬的選項

| 選項 | 隱私承諾 | 費用 | 缺點 |
|---|---|---|---|
| A. 客戶自己的 API 帳號 | 保留「資料只經過客戶帳號」 | 客戶直接支付，數百元 | 客戶多一個帳號；建置時約需十分鐘協助開戶與儲值 |
| B. 你的 API 帳號 | 不成立，需寫進協議 | 算進報價 | 客戶檔案內容經過你的帳號 |
| C. 你的帳號，每位客戶獨立工作區與金鑰 | 同 B | 可分開計算，交付後停用金鑰 | 同 B |

先前的對話中建議 A。
