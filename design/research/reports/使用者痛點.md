# 使用者痛點：非技術使用者用 AI 管理文件

資料日期：2026-10-04。這是《AI 文件管理使用者痛點》的易讀版，內容相同、改為表格與條列。完整的敘述與全部來源連結保留在原檔 [AI 文件管理使用者痛點.md](../research_notes/AI%20文件管理使用者痛點.md)。

## 證據的成色

| 標記 | 意思 |
|---|---|
| 已讀原頁 | 研究時實際開啟並讀過頁面 |
| 僅摘要 | 只看到搜尋引擎的摘要，數字與措辭可能失真 |
| 廠商來源 | 出自有商業利益的業者或其委託調查 |
| 二手彙整 | 部落格或評測轉述論壇意見 |
| 推測 | 研究者的解讀，沒有資料直接檢驗 |

三個影響全篇的限制：

- Reddit、Hacker News、Threads、Dcard 的原始討論串幾乎都沒取得，使用者意見多為二手。
- 多個原始頁面打不開（OpenAI 研究頁、Clio 報告等），相關數字只能靠摘要。
- 目標族群的直接資料幾乎空白：沒有台灣學校行政人員的 AI 使用資料、沒有非技術使用者長期使用 LLM-wiki 的回報、沒有以辦公文件為來源的 LLM-wiki 實測。

## 結論先講

1. **停在聊天層的主因是看不出用途，不是不會用。** 44% 的非使用者認為 AI 幫不上自己的工作，只有 10% 是不知道怎麼用。
2. **「檔案留在本機」只說對一半。** Claude Code 與 Cowork 讀到的內容會送到伺服器處理。
3. **台灣公部門的規範不允許用個人帳號處理個資與校務文件。** 受訪主任的拒絕有法規依據。
4. **現有產品的抱怨分兩層：** 資料進不去，以及進去後不可信。
5. **LLM-wiki 解了整理的負擔，換來查核的負擔。** 「不回頭用」沒有解決。
6. **付費的是自己掌握預算的人。** 受薪者自費的上限大約是一個月的訂閱費。
7. **這筆訪談在受薪公部門職員中很典型，但不能代表會付費的族群。**

## 痛點總覽

## 一、為什麼停在聊天

### 實際用法

| 發現 | 數據 | 來源 |
|---|---|---|
| 主流用法是問資訊、求建議、改文字 | 近 80% 的 ChatGPT 對話屬這三類；超過 70% 與工作無關 | [Marketing AI Institute](https://www.marketingaiinstitute.com/blog/openai-chatgpt-usage-study)（二手） |
| 台灣使用率不到一半，付費意願很低 | 近三個月用過 43.19%；願意付費訂閱 **8.54%** | [TechNews](https://technews.tw/2025/12/18/generative-ai-taiwan-people/)（已讀原頁） |
| 台灣工作用途 | 查找整理資訊 58.8%、會議與文件摘要 36.0%、寫文件郵件 29.1% | [SayDigi](https://www.saydigi.com/2026/09/1455725.html)（公關公司調查，抽樣不明） |

沒有任何調查把「讓 AI 直接編輯檔案、管理資料夾」列為大眾的主要用途。

### 障礙

| 障礙 | 數據或引述 | 來源 |
|---|---|---|
| 覺得幫不上自己的工作 | 不用 AI 的員工中 **44%** | [Gallup](https://www.gallup.com/workplace/694682/manager-support-drives-employee-adoption.aspx) |
| 沒有工具可用 | 16% | 同上 |
| 抗拒改變工作方式 | 11% | 同上 |
| 不知道怎麼用 | **10%** | 同上 |
| 不知道該要求什麼 | 「我想要大家說的那些自動化，但不知道該要求什麼」 | [Julie Kaiser](https://thejuliekaiser.com/claude-cowork-vs-claude-code/) |
| 不信任 | 93% 表達擔憂：虛假與偏誤 64%、過度依賴 60%、隱私 47% | [資策會 MIC](https://mic.iii.org.tw/research.aspx?id=726)（2024 年） |
| 免費版印象差 | 「付費的 gpt 和免費的 gpt 是兩種智商的產品」 | [PTT](https://www.ptt.cc/bbs/WomenTalk/M.1775363916.A.2BC.html)（單一討論串） |
| 終端機嚇人 | 「終端機是真的，而且看起來很可怕」 | [Julie Kaiser](https://thejuliekaiser.com/claude-cowork-vs-claude-code/) |

**含意：** 教操作打不中主要問題。使用者缺的是「我的哪一件工作可以交出去」的具體畫面。

### 年齡

| 年齡 | 用過聊天機器人 | 用於工作 | 來源 |
|---|---|---|---|
| 30–49 歲 | 61% | 43% | [Pew Research](https://www.pewresearch.org/internet/2026/06/17/how-opinions-and-use-of-ai-differ-by-age/) |
| 50–64 歲 | 42% | 29% | 同上 |
| 65 歲以上 | 23% | — | 同上 |

- 使用聊天機器人的自信：18–29 歲 31%，65 歲以上 6%。
- 台灣：40 歲以上 AI 素養各面向明顯較低（[TVBS 報導 TWNIC](https://news.tvbs.com.tw/life/3125043)）。
- 中高齡是低使用率加上低自信。但自費比例上，60 歲以上（33.9%）反而高於 18–29 歲（19.77%），年齡不等於不付費。

## 二、隱私與規範

### 使用者的態度

| 發現 | 數據 | 來源 |
|---|---|---|
| 擔心但照用 | 84% 擔心資料被公開，仍有 30% 輸入機密資訊 | [Cisco](https://investor.cisco.com/news/news-details/2024/New-Cisco-Survey-Shows-Strong-Relationship-Between-Privacy-Awareness-and-Trust-in-AI/default.aspx) |
| 違規使用普遍 | 將近一半員工以違反公司政策的方式使用 AI | [KPMG](https://kpmg.com/xx/en/media/press-releases/2025/04/trust-of-ai-remains-a-critical-challenge.html) |
| 台灣的擔憂 | 68.7% 對個資被 AI 平台不當使用有中高度擔憂 | [自由財經](https://ec.ltn.com.tw/article/breakingnews/5406176) |

受訪主任屬於因為擔心而真的不用的少數。

### 台灣的規範

| 規範 | 內容 | 效力 |
|---|---|---|
| [行政院生成式 AI 參考指引](https://www.ey.gov.tw/Page/448DE008087A1971/40c1a925-121d-4b6b-8f40-7e9e1a5401f2)（2023） | 不得向生成式 AI 提供應保密的公務資訊、個人資訊、未經同意公開的資訊；封閉式地端部署是明文例外；公立學校得準用 | 參考指引，無罰則。逐點內容引自媒體報導 |
| [教育部中小學注意事項 2.1 版](https://www.hs.ntnu.edu.tw/static/webroot/G162269168272913/application/NN177182760887516.pdf)（2026-02） | 優先使用教育版或經學校審查的版本；**不得以個人帳號登入處理學生資料或校務文件**；商用工具應經學校評估 | 注意事項，無罰則 |
| [個人資料保護法](https://law.moj.gov.tw/LawClass/LawAll.aspx?PCode=I0050021) | 公務機關利用個資須在法定職務必要範圍內；受託者視同委託機關 | 法律 |
| 刑法第 132 條 | 洩漏應秘密事項處 3 年以下有期徒刑，過失亦罰；人事考評與個人隱私資料是常見例子 | 法律 |
| 資通安全管理法（2025 修正） | 公務機關不得使用危害國家資安的產品；DeepSeek 已被列入，範圍含公立學校 | 法律 |

**解讀（不是法律意見）：**

- 個人帳號加商用雲端 AI 加真實人事資料：兩份文件字面上都不允許。
- 灰色地帶：機關採購的企業版或教育版、去識別化後的資料。
- 合規出口的共同特徵：由機關或學校決定，不是個人自行判斷。
- 安全的範圍：公開法規、作業流程、空白範本。

### 本機與雲端的真正差別

| 項目 | 事實 | 來源 |
|---|---|---|
| Claude Code | 在本機執行，但會把提示與模型輸出經網路送出 | [Anthropic 文件](https://code.claude.com/docs/en/data-usage) |
| Cowork | 開啟的本機檔案在 Anthropic 伺服器上處理；官方建議不要授權含財務與個人紀錄的資料夾 | [Anthropic 說明](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely) |
| 資料保存 | 消費者方案允許訓練時保存 5 年，不允許時 30 天；商用方案 30 天 | 同上 |
| 完全本機的模型 | 唯一真正不上傳的做法；一般 16GB 筆電只能跑中小型模型，品質與速度有落差 | 工具比較部落格（可信度偏低） |

**誠實的說法：** 檔案本體留在電腦上，但 AI 讀過的內容會送到廠商伺服器處理並依方案保存。

### 不讓別人看文件

- 個資法把受託者視同委託機關；顧問一旦接觸學校的個資檔案，就需要機關正式委託與監督。
- 主任不讓別人看，在法律上是較安全的立場。
- 一般使用者對「安裝人員看到我的檔案」的態度，沒有找到調查。

## 三、現有產品的抱怨

詳細的逐一分析在 [競品分析.md](競品分析.md)，這裡只列痛點。

| 層次 | 痛點 | 例子 |
|---|---|---|
| 資料進不去 | 數量與容量上限 | NotebookLM 每本 50 個來源；ChatGPT Projects 檔案數上限 |
| | 要挑檔、搬檔 | NotebookLM、Projects 都要上傳到另一個容器；Notion AI 只看 Notion 內的內容 |
| | 掃描檔與複雜排版 | 掃描 PDF 被當成圖片，只得到空泛答案；繁中辨識準確度較低 |
| | 路徑與同步 | Cowork 的雲端硬碟占位檔讀取錯誤；Windows 家目錄外的資料夾曾被拒絕 |
| 進去後不可信 | 幻覺 | 多來源摘要看似合理，對照原文是錯的 |
| | 記憶過期 | Cowork 跨工作階段記憶過期後自信地答錯 |
| | **失敗不提示** | 掃描檔讀不到、排程沒跑，工具都不主動說 |
| 用不起來 | 難融入日常工作 | Microsoft 365 Copilot：75% 的 IT 主管這樣說（Gartner 2024） |
| | 靠自學 | 英國 DWP 試行 89% 靠自學，使用者要求依職務設計的速查資料 |

- 只有 Copilot 有量化的棄用證據，其他產品都沒有留存數據。
- 英國 DWP 試行有訓練、對象經挑選，結果是 65% 每天使用。有人陪同上手與全面鋪開的差異很大。
- 台灣公文格式與 ODF 檔沒有任何使用者討論，是資料空白，不是已證實的痛點。

## 四、知識管理為什麼失敗，LLM-wiki 解了什麼

### 失敗的兩層原因

| 原因 | 說明 | 來源 |
|---|---|---|
| 維護太累 | 「維護知識庫最乏味的部分不是閱讀或思考，是記帳」 | [Karpathy](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) |
| 沒有回頭使用 | 「我等著洞見出現，等了又等」 | [Platformer](https://www.platformer.news/why-note-taking-apps-dont-make-us/) |

沒有可靠的放棄率數據，以上是作者的經驗。

### 一般人怎麼管理檔案

- 自估 56–68% 的檔案取回靠點資料夾，只有 4–15% 靠搜尋（[Bergman 等](https://www.researchgate.net/publication/220515581_Improved_Search_Engines_and_Navigation_Preference_in_Personal_Information_Management)，年代較早）。
- 主任的 30 個業務資料夾是多數人的常態。任何要求搬檔或放棄資料夾的方案，都在對抗既有習慣。
- 「每天花 2.5 小時找資料」是估計值而非實測，不宜用在行銷上。

### LLM-wiki 的實測回報

| | 內容 | 來源 |
|---|---|---|
| 解決了 | AI 接手交叉連結與更新；15.5 萬字編成 210 頁 | [Hacker News](https://news.ycombinator.com/item?id=47640875) |
| 新負擔：讀不完 | 人讀懂生成內容成了瓶頸 | [Zenn](https://zenn.dev/tsurubee/articles/llm-wiki-connecting-knowledge) |
| 新負擔：腐化 | 1,900 多頁運作半年後，難題是長期不腐化 | [Obsidian 中文論壇](https://forum-zh.obsidian.md/t/topic/62709) |
| 新負擔：錯誤累積 | AI 之後讀的是 wiki 而非原始檔，錯誤會一再被引用 | [Hacker News](https://news.ycombinator.com/item?id=47640875) |
| 成本 | 每題約 44,000 token、19 份來源匯入約 20 分鐘；該作者改回 NotebookLM | [artemxtech](https://artemxtech.substack.com/p/i-replaced-karpathys-llm-wiki-with) |
| 規模 | 原提案設想約 100 份來源；約 500 頁後需要另加索引 | [104 職場力](https://blog.104.com.tw/andrej-karpathy-llm-wiki/) |

**判斷：** LLM-wiki 解決了維護的負擔，沒有解決「不回頭用」，並新增了查核的負擔。

對非技術使用者的四類障礙：

| 障礙 | 能否靠代建與 plugin 吸收 |
|---|---|
| 安裝與環境 | 可以 |
| 規則設計 | 可以 |
| 訂閱成本與等待時間 | 不能 |
| 無法判斷 AI 寫的頁面對不對 | 不能，只能靠引用回溯減輕 |

## 五、誰付錢

| 族群 | 證據 | 來源 |
|---|---|---|
| 事務所老闆（會計、記帳） | 95% 使用或探索 AI，只有 11% 嵌入流程；障礙第一名是導入時間 **41%**，成本只占 **3%**；只有 20% 看得到回報 | [Financial Cents](https://financial-cents.com/resources/guides/the-state-of-ai-in-bookkeeping-accounting/)（業者調查） |

| 類型 | 價格 | 備註 |
|---|---|---|
| 個人代建（英語市場） | US$597 安裝包；US$1,997 七天建置；客製 plugin US$3,500 起 | [CoworkConsultant](https://coworkconsultant.com/individuals/)，只是開價，沒有成交數據 |

- 供給端最大的困難是讓客戶在付錢前相信有用；買方最常批評的是付錢買到簡報。

## 六、訪談與外部證據對照

| 訪談陳述 | 外部證據 | 判斷 |
|---|---|---|
| 只用聊天問條款、擬郵件 | 多國調查顯示主流用法相同；50 歲以上使用率與自信偏低 | 普遍，證據強 |
| 重視資安，不能上傳外流 | 台灣 68.7% 擔憂；兩份規範明文限制 | 普遍，且有法規依據 |
| 不願讓別人看文件 | 法規上受託者須由機關委託；使用者態度沒有調查 | 法律上合理，普遍程度不明 |
| 約 30 個資料夾依業務分類 | 多數人靠資料夾而非搜尋；台灣無在地調查 | 很可能普遍（推測） |
| 不願付費 | 台灣僅 8.54% 願付費訂閱 | 普遍，證據強 |
| 前期建構與學習成本太高 | 會計業 41% 卡在導入時間；Copilot 試行 89% 靠自學 | 普遍，證據中等 |
| 要一步步教 AI 太花時間 | 沒有找到可引用的來源 | **未證實** |
| 工作沒忙到需要 | 44% 認為 AI 幫不上工作；沒有調查直接問工作量 | 方向一致 |

主任的拒絕是多重理由疊加：預算不在自己手上、省下的時間不變成收入、工作量不重、資料屬個資而受規範限制。

## 七、哪些族群更痛、更可能付費

| 排序 | 族群 | 理由 | 證據 |
|---|---|---|---|
