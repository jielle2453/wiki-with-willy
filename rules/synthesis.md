# 綜合卡怎麼寫
寫給製卡者；note、lint 也讀；answer 不寫綜合卡。編號固定；理由不在這裡。綜合卡一個實體一張，回答「這件事現在怎樣」，每句點得回出處。

## 一、什麼時候寫

- S-01 只寫 `kb cards todo --json` 列出來的：`synthesis_new`（待建）、`synthesis_stale`（待更新）、`synthesis_broken`（有問題）。沒列的不自己起一張。
- S-02 `synthesis_new` 裡 `confirmed` 是 false 的先不寫：在回答末尾問它的 `question`，客戶確認了（`kb entity confirm`）才寫。
- S-03 客戶自己（todo 的 `profile.about`、`entities` 裡 `self` 是 company 或 person 的）不寫綜合卡。
- S-04 一次改的綜合卡被擋「大改動」就停下來，跟客戶說這次要改幾張、為什麼，他說好才 `kb turn approve`。

## 二、放哪、檔頭

- S-05 路徑照 todo 那一項的 `path`：`<型別>/<名稱>/<名稱>.md`，用 Write 寫；夾不在 Write 會建。不寫到別的地方。
- S-06 檔頭照 todo 給的 `header` 一字不改照抄（`整理到`、`更新日` 都是程式算好的）；`檔案卡`、`相關實體` 兩欄程式寫完會重寫，抄錯也沒關係。範本在 `templates/synthesis.md`，它第一行的註解不抄。
- S-07 寫完被打回「綜合卡有錯：…」就照原因改、整張重寫一次。原因是「綜合卡該放在 X」就寫到 X，再跑 `kb entity clean <寫錯的路徑>` 清掉錯的那張。再被打回就停，回答末尾講這張沒寫好與原因。

## 三、正文

檔頭之後：

```
# <名稱>

<一句講這是什麼：「信義王宅的室內裝修案，業主王先生。」>

## 現況
## 紀事
## 推算
## <設定檔第四節的段落，照 todo 那一項的 sections>
```

- S-08 段落照 `sections` 的順序（已含現況、紀事、推算，後面接設定檔第四節的段），一段一個 `## <name>`。`required` 是 true 的段沒內容寫一行 `未知`；其他沒內容整段不寫（推算沒有就不寫）。那段寫什麼以 `hint` 為準。
- S-09 正文 200～1000 字。

### 現況

- S-10 維護式：事實變了就改寫那一點，不在後面追加「後來改成…」。
- S-11 一點一行，每點結尾標出處：依據是檔案卡寫〔f-xxxxxxxx〕（卡的 `編號`），是客戶口述寫〔s-xxxxxxxx〕（todo 那一項 `statements` 的 `id`），是推算寫〔c-xxxxxxxx〕（`findings` 的 `id`）；兩個依據一起撐的就兩個〔〕。
- S-12 兩份檔寫法不同（兩個金額、兩個日期、兩種付款條件），或檔案與口述寫法不同，兩句並列、各帶出處，不替客戶選，也不寫「待確認」。
- S-13 數字照原檔寫、附〔編號〕，不換算、不四捨五入。

### 紀事

- S-14 一行一件：`- YYYY-MM-DD 事〔f-…〕`，日期倒序（新的在上）；口述的那行日期用口述的 `date`、出處寫〔s-…〕。
- S-15 只放決定、改版、關鍵事件；日期是那件事發生的日子，不是製卡日。
- S-16 只增不改：已寫的紀事不刪、不改寫。

### 推算

- S-17 推算是從多張卡算出來的：一行寫結果、算法一句、依據〔f-…〕〔f-…〕、結尾 `（算於 YYYY-MM-DD）`。todo 那一項的 `findings` 每筆照寫一行：`<text>：<how>〔f-…〕〔f-…〕〔c-…〕（算於 <date>）`，依據取它 `basis` 的編號；`stale` 是 true 的那行結尾改寫「依據有變，待重算」，不照舊數字寫成現況。
- S-18 算不出來、或只靠一張卡就看得到的，不放推算。

## 四、待建

- S-19 讀 todo 那一項 `cards` 列的檔案卡（路徑就是 `path`）、`statements` 列的口述與 `rulings` 列的裁示就夠，原檔不用開。
- S-20 要用的數字卡上沒有，才 `kb convert <檔案卡的編號>` 回原檔讀；〔〕裡照樣寫檔案卡的編號。

## 五、待更新

- S-21 先 Read 舊綜合卡，再讀 `added`、`changed` 列的檔案卡；`source` 是 statement、ruling 的項目，內容就在項目的 `text`，照 S-30～S-32 寫。
- S-22 改寫現況；紀事加這次的事（新報價、新會議）。
- S-23 `removed` 的卡講的事：在現況裡拿掉或改寫成還有依據的說法；紀事不刪。
- S-24 整張寫回同一個 `path`，檔頭換成 todo 給的新 `header`。不改的段原樣留著。

## 六、不寫

- S-25 沒依據的推測、對客戶的建議、「待確認」「可能」這類字；要問的在回答裡問。
- S-26 沒在 `statements` 裡的口述不寫（客戶在對話裡說了但沒記成口述的，先記再寫）；別的實體的事也不寫。
- S-27 個資的值：照檔案卡，只寫種類（「有王先生的聯絡電話〔f-…〕」），不寫號碼。

## 七、有問題的卡

- S-28 `synthesis_broken` 每項有 `reason`：照原因改、整張重寫。原因是「綜合卡該放在 X」就照 S-07。
- S-29 原因是「還沒跟客戶確認名稱」：照 S-02 先問。原因是「這是你自己」「這個實體已移除」：那張不用留，回答末尾跟客戶說一句，請他自己刪。

## 八、口述與裁示

- S-30 `rulings` 有口述為準：那件事的現況以口述那句為準放前面，原檔的寫法接著寫「原檔寫 X」帶〔f-…〕。
- S-31 `rulings` 有不採用：現況不引用那幾張卡；紀事已寫的照留，不再新增。
- S-32 一句話的依據有檔案卡也有口述就兩個都標。
